# Lab 2: Okta-to-Okta SAML 2.0 Federation

> **Status:** ✅ Complete
> **Platform:** Okta Workforce Identity Cloud (Admin Console)
> **Skills:** SAML 2.0, IdP/SP configuration, inbound federation, account linking, Just-In-Time (JIT) provisioning, IdP profile extension, System Log troubleshooting

---

## 📌 Objective

Build a working **SAML 2.0 federation** entirely inside Okta. A custom SAML app plays the **Identity Provider (IdP)** and an inbound **SAML Identity Provider** plays the **Service Provider (SP)**. The goal is to configure both sides by hand, connect them, and prove the federated sign-in works from the System Log.

## 🧠 Why This Matters

Most SAML setups only show one side: Okta acting as the IdP for a SaaS app. Building both sides shows what each one needs from the other and why each setting exists:

| SAML concept | Where it lives in this lab |
|---|---|
| **IdP SSO URL**: where the SP sends users to authenticate | `SAML 2.0 INTG` app → Sign On tab |
| **IdP Issuer**: the IdP's unique identity | `SAML 2.0 INTG` app → Sign On tab |
| **X.509 signing certificate**: lets the SP verify the assertion wasn't tampered with | Exported from the app, uploaded to the Identity Provider |
| **ACS URL**: where the IdP POSTs the SAML response | Generated by the Identity Provider |
| **Audience URI (SP Entity ID)**: who the assertion is intended for | Generated by the Identity Provider |
| **NameID**: the identifier used to match the user | Okta username, format EmailAddress |

## 🏗️ Architecture

```
┌─────────────────────────┐   signed SAML assertion (HTTP POST)   ┌──────────────────────────────┐
│   SAML 2.0 INTG app     │ ────────────────────────────────────► │  SAML 2.0 IdP (inbound IdP)  │
│   (IdP side)            │   NameID + firstName, lastName,       │  (SP side)                   │
│   signs the assertion   │   email, groups                       │  validates, matches, links   │
└─────────────────────────┘                                       └──────────────┬───────────────┘
                                                                                 │
                                                                                 ▼
                                                                       Okta session established
```

### The dependency loop

SAML has a chicken-and-egg problem: the IdP needs the SP's **ACS URL and Audience URI**, but the SP needs the IdP's **SSO URL, Issuer, and certificate**, and neither exists until the other side is created. I solved it with **placeholder values**:

1. Create the IdP app with placeholder ACS and Audience values
2. Use its real SSO URL, Issuer, and certificate to create the SP
3. Go back and replace the placeholders with the SP's real ACS URL and Audience URI

## 🔧 Troubleshooting: What Went Wrong and How I Fixed It

### 1. Google 405: POST is inappropriate for the URL
![Google 405](screenshots/error-01-google-405.png)

- **Cause:** The app still had the `https://google.com` placeholders, so Okta POSTed the SAML response to Google, which doesn't accept SAML.
- **Lesson:** The 405 actually proved the IdP side worked. Okta built and sent the assertion; it just sent it to the wrong place.
- **Fix:** Replaced the Single sign-on URL and Audience URI with the Identity Provider's real ACS URL and Audience URI.

### 2. Okta 400: Login Failed (GENERAL_NONSUCCESS)
![Okta 400](screenshots/error-02-okta-400.png)

The error page is generic, so I went to the **System Log** for the real reason:

![System Log Unable to JIT](screenshots/error-02b-system-log-unable-to-jit.png)

- **Log:** `Authenticate user via IDP – FAILURE: Unable To JIT` and `Create okta user – FAILURE`
- **Cause:** The test user already existed in Okta, but **automatic account linking was disabled**. The IdP couldn't link the assertion to her existing account, so it fell back to JIT provisioning, which failed because the user already existed.
- **Fix:** Enabled **Account link policy → Enable automatic linking**, with **Exclude admins** checked as a guardrail.

### 3. Unknown Profile Attribute
![Unknown Profile Attribute](screenshots/error-03-unknown-profile-attribute.png)

- **Log:** `Authenticate user via IDP – FAILURE: Unknown Profile Attribute`, one second before the SUCCESS event
- **Cause:** The assertion included a `groups` attribute that wasn't defined in the inbound IdP's user profile. Okta flagged it but still finished authentication.
- **Fix:** In **Directory → Profile Editor → SAML IDP User**, added a `groups` attribute (string array, external name `groups`). On re-test, the log went straight from app SSO to **Authenticate user via IDP – SUCCESS** with no failure.

## 🔐 Security Considerations

- **Placeholders are temporary.** Leaving them in place sends signed assertions to a third party, which is exactly what happened in Troubleshooting #1.
- **Signed assertions.** The SP validates every response with the IdP's X.509 certificate, so a tampered or forged assertion is rejected.
- **Auto-linking is powerful.** It lets an external IdP sign in as any matching Okta account, so I excluded admins. In production it should also be scoped to specific groups.
- **JIT creates accounts automatically.** In production it should be paired with group rules and attribute filtering.
- **Scope group claims.** The `groups` filter `.*` sends every group a user belongs to. That's fine for a lab, but production should use a narrower filter (for example, `Starts with: SAML-`) so unrelated memberships aren't exposed.
- **Sensitive values redacted.** The org domain, IDs, emails, and IP addresses are blurred in all screenshots.

## 💡 Key Takeaways

- Configured SAML **manually**, entering the SSO URL, Issuer, and certificate by hand. In production, **metadata exchange** (especially a metadata URL) is preferred because the SP can pick up IdP certificate rotations automatically instead of breaking SSO when a certificate expires.
- The friendly error page rarely tells you the real cause. **The System Log does.** All three issues were diagnosed from log events, not guesswork.
- Account matching, linking, and JIT are separate decisions: *how do I find the user*, *may I connect to them*, and *what if they don't exist*.
